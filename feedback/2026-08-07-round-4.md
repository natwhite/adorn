## 1. The verdict, and why it is expiring

**Round 3 said "do not adopt" because adorn could not do the job. That is no longer true anywhere we
tested.** The remaining objection is about us, not you: today adorn could replace ~68 of our 8,077
lines, for two runtime dependencies where we currently have zero. Our DEC-022 refuses that trade, and
it is right to.

**But that arithmetic measures adorn against the codebase we have, and the interesting question is
the one the project owner actually asked:**

> _"I would prefer we build out the lib so that future projects don't need all the tests and docs and
> guards that we've had to build here."_

That reframes it. `0.84%` is the wrong number, because the surface where your thesis has more than one
consumer **does not exist in our repo yet** — and it is now being designed. We are planning a
Realtime voice layer whose classifier needs a JSON Schema *and* a runtime validator for each of ~14
inbound variants, per session, kept in agreement by hand. That is the trigger round 3 said to write
down. It is no longer hypothetical, which means the adoption question resolves within weeks rather
than someday.

Everywhere else in our codebase **N = 1**: `DTMF_PATTERN`, `DATE_PATTERN`, `PHONE_NUMBER_PATTERN` each
exist once with one consumer. There is no second artifact for a first to drift from, which is
precisely the problem adorn exists to solve. **You do not have a library that is too weak for us; we
have a codebase that has not yet grown the problem.**

## 2. Three asks that survive, ranked

### 2.1 A descriptor-first, optional-aware object descriptor

**The thesis fails at the commonest shape.** `toolSchemaFrom` can mark a param optional
(`schema.ts:410`) and emits a correct schema with `required: []`. But it returns JSON, not a
predicate. The only descriptor that validates a fixed-key object is `Shape`, which needs a class
(`object.ts:208-229`) and **requires every contracted field to be present** (`object.ts:140-145`).

So for the actual shape of an HTTP body — and for the actual shape of a tool call with an optional
argument — the schema is one declaration and the validation is N separate `Verify.check` calls. In a
library whose whole claim is that the two cannot drift, they are not derived from one statement at
exactly the shape a JSON object has.

```ts
ObjectContracts.Fields({
    seq: NumberContracts.Integer(),
    slotInput: {descriptor: SLOT_INPUT, optional: true},
});
```

Taking `ToolSchemaFromInput.params`'s own input shape, so the two structurally cannot disagree. No new
vocabulary — `ToolParamSpec` already defines it. **This is the one I would put first.**

### 2.2 `expected?: string` on a failing `CheckResult`

`path` locates the failure; `message` still describes the container. Observed, on
`ArrayOf(OneOf(['alice','bob']))` given `['alice','zzz','bob']`:

```
path      : [1]
message   : Value Error: subjects expected an array of one of "alice", "bob" but received [REDACTED]
```

Composed for a caller that becomes `subjects[1]: expected an array of …`, which contradicts itself —
index 1 is not an array. Our hand-written version says `slotInput.when must be a string`, which is
shorter and correct.

The innermost failing descriptor is already in `locate`'s closure (`array.ts:122-124`,
`object.ts:71-73`). Returning its `describe()` on the `ok: false` arm is the same shape of change
GAP-19 already accepted one level up. **This is the only remaining defect that would make us hesitate
on an endpoint whose error message is its contract.**

### 2.3 Run `detectUnsatisfiableStack` inside `toolSchemaFrom`

GAP-20 is marked fixed, and it is — on the **decorator** path (`ContractInstaller.ts:330,356,383`).
`toolSchemaFrom` does not route through the installer. Observed:

```
toolSchemaFrom({params: {subjects: {descriptor: [ArrayOf(NotEmpty()), OneOf(ROSTER)]}}})
  -> no diagnostic
  -> {"type":"array","enum":["alice","bob"],"items":{"type":"string","minLength":1}}
```

Same unsatisfiable schema round 3 §3.4 reported, same silence — now on `ToolParamSpec.descriptor`'s
array form, which exists precisely to stack descriptors, **on the path your README now recommends.**
The trap moved rather than closed. Same detector, same data, one call earlier.

_Lower:_ export `defineConstraint`. GAP-22 exported the `ConstraintDescriptor` **type** without the
factory that builds one, so a consumer can name a custom constraint but not make it.

_Also narrow, and it came out of a security detail:_ `isDictionary` (`object.ts:54-62`) validates with
`Object.keys(...).every(...)` and hands back **the caller's object**. Our HTTP handler must therefore
still rebuild it key-by-key to drop an own-property `__proto__` — verified, it survives `Verify.check`
intact. That is not a bug (a validator that mutated its input would be worse), but it means adorn
removes zero lines from the one loop in that function carrying security weight. **An opt-in
`{rebuild: true}` that returns a fresh null-prototype object would remove it.**

## 3. The bigger ask — what we built by hand, and which of it is yours

Taking the stated goal seriously: here is the machinery this project had to build, honestly sorted.
**Most of it is not adorn's business, and saying which is the useful part of this section.**

| What we built | Generic? | Belongs in adorn? |
| --- | --- | --- |
| Result unions — `{kind:'ok'} \| {kind:'error'}`, **seven of them** | yes | **narrowly, yes** — §3.1 |
| Four-valued write outcomes + idempotency + bounded retry + fault injection | **very** | **no — an addon** (§3.2) |
| Pre-verification disclosure bound, enforced at two emit points | yes | **partly** — §3.3 |
| Closed inbound union + per-session enums | yes | **already yours** — `toolSchemaFrom` |
| Pure reducer + described effects, deep-equality tested | yes | no — that is an architecture, not a library |
| Append-only disposition ledger, last-write-wins | no | no — domain |
| Layering guard (`core/**` imports nothing downward) | yes | no — `dependency-cruiser` exists |
| Deterministic renderer keyed on intent | no | no — domain |

### 3.1 Result unions — seven, and you already ship the eighth

Our codebase carries `SelectionResult`, `SlotBuildResult`, `TurnResponse`, `JsonBody`, `AnswerResult`,
`AnswerBody`, and the runtime's `{terminated?}`. Each is hand-rolled, each is slightly different, and
`CheckResult` would make eight. DEC-018 ("failure is a returned value, not a throw") is the decision
that produces them and we would make it again.

You already have an opinion here, shipped, in `CheckResult`. **Making that type reusable and its
guards exported — not a monad library, not combinators, just the shape and its narrowing helpers —
would let a consumer stop reinventing it per module.** It is the smallest possible thing that
addresses "future projects shouldn't have to build this", and it is genuinely in scope for a library
whose thesis is that failure is data.

The counter, which I believe is real: every TypeScript project has one of these, and none of them
agree. Shipping a ninth flavour helps nobody unless it is the one that comes with the validator that
produces it. **So: yes, but only as `CheckResult` generalised — not as a standalone `Result<T,E>`.**

### 3.2 The write-outcome contract — the most valuable thing here, and it must not go in adorn

This took us four decisions (DEC-013, 013a, 013b, 013c) and a testability mechanism (SMELL-9's
injectable `FaultPolicy`) to get right:

- **Four values, not three.** `committed` / `rejected` / `unknown` / `unavailable`. The split that
  matters is `rejected` vs `unavailable`: a slot taken while the caller was deciding, and the
  database being unreachable, are both non-retryable but want opposite responses — one is ordinary
  business, the other means nobody on this call can make progress.
- **`unknown` is never cached, and is safely replayable** only because every write is expressed as an
  idempotent set rather than a delta.
- **Idempotency keys are attempt-scoped and session-salted**, because a key derived from content
  serves a stale rejection forever, and an unsalted key collides across households the moment the
  cache is shared.
- **Bounded transport retry sits below the idempotency cache**, so a transient fault never reaches
  the caller and `unavailable` means the retry was already spent.

Every project that writes to a system of record needs exactly this, and most get it wrong — usually
by being two-valued. It is the strongest candidate in this document for "future projects shouldn't
have to build this".

**And it is not validation.** Putting it in `adorn` proper would be the scope creep that turns a
focused library into a framework, which is the thing most likely to kill it. You already have the
right structure for this — `addons/otel` and `addons/test` — so it wants to be a sibling addon with
its own name and its own README, sharing nothing with the constraint engine but the repo.

I am flagging it rather than asking for it. It is a bigger piece of work than the three asks in §2,
and it should not be started until those land.

### 3.3 The disclosure bound — `src/Sensitive` exists but not in a shape we can use

We enforce "no patient name before the caller is verified" at **two** points on purpose — once in the
reducer that builds the payload, once in the renderer that speaks it — because it is a rule about what
may be _emitted_, not only about what may be _spoken_, and a second consumer of that payload would
otherwise bypass a single chokepoint.

You have `src/Sensitive` and `@Sensitive`. We cannot use it: our types are `type`-shaped throughout —
`Presentation`, `Effect`, `Transition`, every wire type — and there is no class to decorate. Round 3
raised the shape of this and round 4's agent deliberately did **not** ask for it, on the grounds that
we have no consumer and would be asking on someone else's behalf.

The stated goal changes that calculus, so I will ask, narrowly: **a way to mark a field sensitive
without a class, plus a projection that lists the sensitive paths.** The projection is the valuable
half — it lets a renderer, a logger or a transcript writer _assert_ that it emitted none of them,
which is a test we currently write by hand and by name for each intent.

What I am **not** asking for is redaction-on-serialise. We want the assertion, not the magic.

## 4. The risk, stated because I am the one creating it

**One consumer's wish list is the worst possible design input for a library**, and this is now the
fourth document I have sent you. Everything in §3 is a request to make adorn look more like the shape
of one paediatric appointment-confirmation test bed.

Three things I would hold onto if I were you:

1. **The §2 asks are the ones with evidence.** Each came out of a compiled probe that failed or
   produced something wrong. §3 is extrapolation from one codebase.
2. **Your README says adorn "rejects an invalid value; it never silently coerces, defaults, or
   transforms one."** That sentence did more to make this round easy than any feature — it let me
   rule out four surfaces immediately (our slot builders coerce `"alice, bob"` into an array, and are
   therefore contractually not yours). **A library that says clearly what it is not is easier to adopt
   than one that says yes to everything.** Guard it.
3. **Half of adorn is unusable to us and always will be** — `setViolationPolicy` and the ambient
   configuration family, `@Log`/`@Observe`, anything that throws, anything needing a class. That is
   not a criticism and it does not need fixing. It is a scoping fact, and if we adopt, we will pin it
   with a lint rule that only `Verify.check` and the `*Contracts` namespaces may be imported from
   anywhere reachable by a pure reducer.

## 5. The one thing that would most increase confidence, and it costs one API call

**Q-31 is still open** (`adorn/docs/ISSUES.md:126`): no `toolSchemaFrom` output has ever been
round-tripped through a real LLM provider. Four rounds of feedback have now judged those schemas by
inspection — including this one, including the probe that produced the `splitFor` schema above.

It is the largest unverified assumption underneath the only real case for adopting adorn here, and
closing it is one call to one provider with one generated schema. **If a provider rejects or
mis-fills a schema `toolSchemaFrom` emits, §1's entire argument collapses** — and better to find that
out now than after we have built a classifier on it.
