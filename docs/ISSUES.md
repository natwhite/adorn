# adorn — Issue Tracker

Running log of bugs, code smells, infrastructure gaps, and open questions found while working on adorn.

> **Maintenance convention:** this file is kept current as work proceeds. Anything encountered — a bug, a smell, a feature idea, an unanswered question — gets an entry here *when it is found*, even if it is not being fixed at the time. Architectural choices go in [DECISIONS.md](DECISIONS.md) instead. Large feature directions live in [vision.md](vision.md); this file tracks only the pointer, not the prose.

**Status legend:** `OPEN` · `FIXED` · `PARTIAL` (fixed in part, residue remains) · `DEFERRED` (accepted, scheduled) · `WONTFIX` · `MOVED` (the code it describes has been removed from this package; the entry is retained because the finding outlives the code and must travel with it — see **IDEA-8**)

## IDEA-8 — `@adorn/rx`: the reactive module, and the knowledge owed to it

**Status:** OPEN · raised when `rxjs` and `@Memoize` were removed from core (GAP-6, DEC-019)

Core adorn now depends on **no** reactive library. `@Memoize` was deleted and `rxjs` removed from the
manifest entirely, which closed GAP-6 — a consumer can `require('adorn')` with nothing but `tslib` in
their tree. The user's intent when directing that removal was explicit and is the reason this entry
exists rather than a tombstone:

> *"We can drop rxjs and Memoize for now, but I imagine we'll want a separate module with added
> functionality that ends up including it."*

**Expected shape.** A separate package (`@adorn/rx` or similar) taking `rxjs` as a real dependency —
which it can, being opt-in — and providing: `@Memoize` for Observable-returning methods; Observable
timing for `@Time` (the interop seam for this **already exists in core**, see below); and the
flow-control decorators `vision.md` names, which is what the deleted `queue.ts` stub was gesturing at
(SMELL-6).

**Two seams in core are already built for this and should not be removed as dead code.**
`@Time` keeps its Observable branch, reaching rxjs only through a guarded lazy `require` in
`loadObservable()`; with rxjs absent it degrades to `settled: false` rather than reporting a
meaningless zero. And `isObservableLike` in `Time.ts` preserves the `instanceof`-then-duck-type
ordering that BUG-5 established. Deleting either would cost more than it saves. The one open question
attached to that seam is **SMELL-16**, whose fix (`setObservableConstructor()`) is now unblocked and
should be decided *here*, since it is a public-API question and this is the module that needs it.

### Findings that must travel — do not rediscover these

The entries below are marked `MOVED` in the tables above rather than deleted. Each one cost real
effort, and every one of them is a defect a from-scratch reimplementation will walk straight back
into. The deleted implementation is recoverable from git history at
`src/MethodDecorators/promise/Memoize.ts` (with its 772-line test file alongside it), and reading it
is cheaper than re-deriving it.

| Carried finding | Why it will otherwise recur |
|---|---|
| **BUG-9** — `publishReplay()` + `refCount()` **re-executes a non-completing source** while still replaying the stale buffer. The fix is `shareReplay({bufferSize: Infinity, refCount: false})`. | This is the pairing every "memoize an Observable" tutorial reaches for, and it *looks* correct because completing sources — HTTP calls, the intended use — never expose it. |
| **The cost of `refCount: false`, accepted deliberately.** The source subscription is established on first subscribe and never torn down for a source that does not complete, so an endless stream keeps producing and its replay buffer keeps growing for as long as the cache entry lives. | It is a real leak for infinite streams and will look like a bug to whoever finds it. It is the price of "run this once": a decorator that memoizes cannot also tear down and re-run. Ship it stated, not discovered. |
| **BUG-10** — memoized failures become **retryable** as a *consequence* of BUG-9's fix, not by separate design (`shareReplay` discards its subject on error). Residual, deliberately unaddressed: while a source keeps failing, every new subscriber triggers its own attempt, so failures are not de-duplicated. | Because it was never chosen, reverting to the wrong operator silently reverts this too — and retry policy is a caching-framework concern that should stay out of scope on purpose. |
| **BUG-11** — cache-key collisions for exotic containers. `Map`, `Set`, typed arrays, `DataView`, `ArrayBuffer` must be described **explicitly**; anything else exotic (detected via `Object.prototype.toString`) must fall back to **identity**. | The naive own-enumerable-keys approach keys every one of them as `{}`, so `f(new Map([[1,2]]))` returns the cached result for `f(new Map())`. The governing principle: **a miss costs performance, a wrong hit costs correctness, and the two do not trade.** |
| **BUG-15** — still **unsolved**. A user class hiding all state behind private fields, closures, or prototype getters reports no own enumerable keys and keys as empty, colliding across instances. | Arrives as live work. The reason it is unfixed is the valuable part: both general remedies are worse than the bug — identity-keying every class instance destroys the structural hit that makes memoization worth having (`fetch({id: 1})` is the motivating case), and walking prototype getters invokes arbitrary user code during key construction. |
| **BUG-3** — storage is a per-decoration, per-instance `WeakMap<instance, Map<argKey, value>>`, **not** a prototype-level cache. | The prototype cache is the obvious implementation and is wrong three ways at once: shared across instances, never invalidated, and ignoring arguments. `WeakMap` ephemeron semantics also mean a cached value closing over its own instance is not a leak — which is what makes the design work at all. |
| **BUG-5** — validate the return value with `instanceof` **first**, then duck-type on `subscribe` *and* `pipe`. | `instanceof` alone fails across realms when a second copy of rxjs is installed. Duck-typing alone accepts things that cannot be piped. Both checks are needed for different reasons. |
| **Cold-safety**, above all. Nothing may be subscribed at decoration or at call time. | Eagerly subscribing to cache a *value* duplicates side effects and breaks cold Observables — the single most likely correctness bug in this whole area. |
| **Not provided, deliberately:** invalidation, TTL, size limits. A cache entry lives as long as its instance, and is unbounded in distinct argument keys per instance. | A long-lived singleton called with unbounded arguments grows without limit. Known and accepted for a correctness-only decorator; a real caching vocabulary is a `vision.md` item, and that is the right place for it. |

**One test-fidelity note, since it is the kind of thing that silently rots.** `Time.test.ts` now covers
the Observable branch against a hand-rolled `MockObservable` injected through a *virtual* jest mock,
because there is no rxjs to test against. That verifies the small contract `@Time` relies on, not
genuine rxjs interop. When this module lands and brings rxjs with it, those tests should be run
against the real thing again.
