# adorn — Issue Tracker

Running log of bugs, code smells, infrastructure gaps, and open questions found while working on adorn.

> **Maintenance convention:** this file is kept current as work proceeds. Anything encountered — a bug, a smell, a feature idea, an unanswered question — gets an entry here *when it is found*, even if it is not being fixed at the time. Architectural choices go in [DECISIONS.md](DECISIONS.md) instead. Large feature directions live in [vision.md](vision.md); this file tracks only the pointer, not the prose.

## Open questions

| ID | Status | Question |
|---|---|---|
| Q-1 | OPEN | `Positive` accepts `0` (it rejects only `value < 0`), but "positive" strictly means `> 0`. The name and the semantics disagree. Pick one and apply it consistently across `Positive`, `Verify.positive`, and any future `Negative`. |
| Q-2 | OPEN | Should preconditions guarding *untrusted external* input ever be strippable in production? A single blanket toggle is unsafe — internal self-checks can be stripped, boundary checks generally cannot. Tracked as DEC-008. |
| Q-3 | OPEN | Generating meaningful arbitraries for *arbitrary hand-written predicates* is unsolved — a closure is a black box to a generator. Built-in constraints are tractable via their descriptors; **user-written predicates are not**, and generate-and-filter degrades badly for narrow ones. Consequence to state publicly rather than bury: **"decorate your code, get a fuzz suite" is not deliverable.** Coverage is partial by construction. |
| Q-4 | OPEN | **Descriptor/predicate drift** — the worst failure mode this goal introduces. If a descriptor says `min: 0` while its predicate checks `> 0`, generated documentation *looks* authoritative while disagreeing with what is actually enforced. Mitigated by deriving predicates from params (DEC-010), but any escape hatch permitting hand-written predicates reopens it. |
| Q-5 | OPEN | **Postcondition expressiveness**, not plumbing, is the real difficulty. Useful postconditions often need prior state and can be as hard to write correctly as the implementation they describe. Adoption may stall here regardless of how good the tooling is. |
| Q-6 | OPEN | Registry introspection becomes **semver-relevant** the moment a projection binds to it (DEC-011). It was internal and freely changeable before; what subset becomes public API is undecided. The read surface is now concrete — `getContracts` / `getContract` / `getContractedClasses` — so this needs settling before a projection binds to it. |
| Q-7 | OPEN | **`NaN` satisfies every numeric constraint.** The originals test `value < min` / `value > max`, and every comparison with `NaN` is `false`, so `NaN` never triggers a violation. Deriving the *obvious* `v => v >= min` would flag it — the two forms disagree on exactly this one input, so switching would be a silent behaviour change under a refactor. P1.0 preserved current behaviour as `!(value < min)` and pinned it with a test. Settle it deliberately in P3.3, where uniform type guards belong. |
| Q-8 | OPEN | **Plan text contradicts DEC-010.** P1.0's prose describes `defineConstraint` as building from `{kind, constraint, params, predicate, message}` — listing `predicate` as an *input* — while the bullet below it and DEC-010 mandate derivation. P1.0 was implemented per DEC-010 (no `predicate` input exists). The stale prose must be corrected: a hand-written-predicate input is precisely the escape hatch Q-4 warns reopens drift. |
| Q-9 | **FIXED** | `getContractsForClass(ctor)` added to the registry (DEC-018). Returns both bands as a flat, deterministically ordered list of `{key, contract, isStatic, target}` — instance methods first, then statics — so the "walk both" rule lives in the registry once instead of being re-derived by four projections. **Residual work:** `src/Projections/docs.ts` still hand-rolls the two-band walk and should be refactored onto this (behaviour-neutral; not done here only because that file is owned by another agent). |
| Q-10 | **PARTIAL** | **Arity now recovered for ordinary signatures.** `getParamNames` returns *every* declared parameter, so undecorated positions get entries and `Order.place(sku, quantity, note)` renders complete. Guarded by `isTrustworthySignature`: if any recovered name is not a plain identifier (destructuring, rest), names are still written to decorated positions — keeping registry and message in agreement — but **no position is invented**. **Residual:** destructured/rest signatures still yield no arity, and decorated positions within them get misaligned names (pre-existing, from the `toString()` parse). `design:paramtypes.length` would be a reliable arity source where metadata exists; that needs its own mechanism, and still blocks a faithful OpenAPI emitter. |
| Q-12 | **FIXED** | Settled as **installation implies enumeration** (DEC-016): `@Validate()` now registers its owning class, and `getContractedClasses()` means "classes adorn has installed enforcement on". Decided on asymmetry of failure — an unenforced contract eventually surfaces when something gets through, while a contract that is enforced but missing from a generated artifact never does. Adorn must not guarantee at runtime what it will not admit to in a document. Suppressing a class from an artifact is a projection-level filter, not an enforcement decorator's job. One characterization test was inverted; see DEC-016. |
| Q-13 | **FIXED** | Comment corrected, source unchanged. `MethodContract.installed` now states plainly that it does **not** drive the warning and cannot: `CreateSimpleDecorator` closures never reach the registry (SMELL-14), so a sweep over `installed === false` would skip exactly the classes most likely to be silently broken. The adapter-side pending set in `ContractDiagnostics` remains the correct driver — it is told about every authoring form. The flag stays accurate for methods the registry holds, and is what a projection reads to mark a contract recorded-but-unenforced. The two sources were deliberately **not** folded together. |
| Q-11 | OPEN | **`pre`/`post` are reserved but unreachable** — the registry ships the slots with no writer, so no caller can populate them. Harmless for documentation, but the fuzzing projection cannot function without them: postconditions are the oracle (DEC-006). A writer is a prerequisite for that projection, not a nicety. |
| Q-14 | OPEN | **Subclass field-contract inheritance is undecided.** A subclass redeclaring a decorated field currently *replaces* rather than inherits the base contract (own-scoped, matching `ContractRegistry`). Pinned by a test labelled `OPEN QUESTION`. Whether a subclass should inherit, be allowed to strengthen, or be forbidden from weakening a field precondition is a **Design-by-Contract / Liskov** decision (see `contract-driven-development.md` §2.5) and was deliberately not invented by the implementer. |
